\subsection{Vouchers (\tr{CLAIM})}\label{app:claim}

A voucher is a BIP-340 signature by the source leaf's owner over
\[
H_{\mathsf{voucher}}(\mathsf{tree\_id} \,\|\, \ell_{\mathrm{src}} \,\|\, \ell_{\mathrm{claim}}),
\]
verified with \op{CHECKSIGFROMSTACK}. Under spec~0.10.0 every tier binds
$\mathsf{tree\_id}$, a constant fixed when a tree is created and
inherited by the cohorts detached from it, in place of $m$, which names
a rule set and so is shared by trees created with the same parameters;
a voucher therefore verifies only in its own lineage, and survives a
detach. The claim leaf must keep the source's evictor key and a lease no
later than the source's (spec~0.10.0).
\tr{CLAIM} is two steps: the source
leaf's amount is reduced by the claim amount and its $\mathsf{seq}$
advanced by one (or the position emptied if drained), then the claim leaf
is placed at an empty position. The total is unchanged. Replay is
impossible because the first step changes the source leaf, so the signed
message never again matches a leaf in the tree; $\mathsf{seq}$ prevents a
balance that later returns to an earlier value from re-enabling an old
voucher. Because a voucher lets an owner move value with a lone
signature, leaves whose balance is not the owner's alone set
$\mathsf{seq}$ to the tier's $\mathsf{SEQ\_FINAL}$ (\S\ref{sec:channels}),
whose successor does not fit in four bytes, so the \tr{CLAIM} script
rejects them. Vouchers are the mechanism for
operator-to-member push payments without the operator's later
participation.

\paragraph{Hash-locked vouchers (\tr{CLAIM}$^{h}$).} Adding a payment hash
to the signed message, under its own tag, and requiring the preimage at
redemption turns a voucher into a hash-locked cheque that can be paired
with a channel-leaf HTLC or a Lightning invoice carrying the same hash.
It is not an HTLC and the pairing is not atomic: the value stays in the
source leaf, and until the redemption confirms the issuer can void the
cheque with a conflicting \tr{EXIT} or \tr{SPLIT} of that leaf, so the
redeemer bears issuer risk for that window, which contention on the tree
output lengthens. The
script does not compare a witness-supplied hash against the preimage: it
computes $\mathrm{SHA256}(\mathsf{preimage})$ and feeds it into the signed
message, so a wrong preimage fails as an invalid signature. That costs one
hash opcode, eight bytes of script in every tier, and
no opcode beyond those \tr{CLAIM} already needs. The separate tag is
load-bearing: reusing $H_{\mathsf{voucher}}$ for both forms would let a
redeemer strip the hash lock.

The variant adds ordering, not security. It cannot create an on-chain
deadline, because script can require that a spend not happen before a
height but not that it happen before one, and the value backing a voucher
never leaves the source leaf, so there is nothing to refund; deadlines live
in the other leg of the swap, and an issuer retires an unredeemed voucher
by advancing the source leaf's $\mathsf{seq}$. Redemption publishes the
preimage, which is what settles the other leg and also what obliges a
redeemer to secure its own leg first.

\paragraph{Exit-key consent (\tr{CLAIM}$^{x}$, \tr{CLAIM}$^{hx}$).} The
FULL tier also builds both forms with one further signature over the
transaction by the source leaf's exit key, as \tr{UPDATE}$^{x}$ adds to
\tr{UPDATE}: 8 bytes of script over the plain form (\tr{UPDATE}$^{x}$'s
seven and one \op{SWAP}) and 64 of witness. Its use is a credit leaf
owned by an issuer and exiting to one recipient: every voucher against it
pays that recipient, whose own redemptions carry the exit-key signature
at no cost, and the issuer cannot carve the leaf even with a voucher it
signs to itself.
