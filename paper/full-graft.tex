\section{Grafting and Whom It Trusts}\label{sec:graft}

\tr{JOIN}$_h$ replaces an empty node $\Emp_h$ with a node $(R_h, s_h)$
that the operator built off-chain from up to $2^h$ new leaves, and adds
$s_h$ to the tree output. Nothing below height $h$ appears on-chain and
the script walks only the $D - h$ levels above the slot, so a larger
cohort is a smaller transaction (Table~\ref{tab:graft}). Each height is a
tapleaf fixed at creation; the sparse profile batches only by
\tr{JOINK}$_K$.

\paragraph{What the covenant checks.} The predicate requires that the
slot held $\Emp_h$, that output~0 carries $S + s_h$, and the operator's
signature. It sees a hash and a sum and cannot tell a real cohort from
random bytes, which is what makes the graft constant-size and is the
source of every trust question. \lean{join\_sound} states the
consequences: the slot was empty, output~0 is the old sum plus $s_h$, and
for every tree whose root is the grafted node the new root is the old
tree with it inserted. A graft therefore cannot move, shrink or rewrite
an existing leaf. A node with no preimage is an opaque node of $\Ftree$:
its $s_h$, exactly the value the graft added, is frozen, every other leaf
stays payable (Theorem~\ref{thm:cons} holds whatever a sibling is), and
the terminal exit is lost.

\paragraph{Who carries what risk.} Existing members never sign and take
no risk. The operator can fill an empty aligned slot with any node it
signs and funds, so an opaque or zero-sum graft freezes only the value it
brings and wastes only slots no one else could fill. Assurance is needed
only by those who put money in. A member funding with an input checks the
unsigned transaction (the slot folds as $\Emp_h$ to the current root, its
leaf folds to $(R_h, s_h)$ with sums recomputed, output~0 commits to the
new root for $S + s_h$) and signs over all outputs, so its input can only
be spent into a root containing its leaf. A member buying in off-chain
checks the same path against the confirmed root before paying over
Lightning, or pays through a hash-locked voucher (\S\ref{sec:receive}).
Neither checks anyone else's leaf: leaves whose paths verify sum to at
most the root, so a co-member's bad leaf cannot make a good one unpayable.

\paragraph{Funding.} In an operator-funded graft the operator supplies
$s_h$ from the input the model already counts and members buy their
balances off-chain; the operator bears the credit risk of a member who
never pays, a risk to it and not to other members. In a member-funded
graft each member adds an input and signs one transaction after the
cohort is fixed, so one absent member stalls the cohort and the rest
retry (a liveness cost, not a safety one), and the saving against an
on-chain batch, $43\vB$ per output, is gone. Had the operator grafted a
node with no tree behind it, every member's check would fail, nobody
would pay, and only the operator's own coins would be frozen.

\paragraph{Designing a cohort.} The slot the operator picks is what later
batching depends on, and a cohort should share a lease, since one leaf
the operator admits with a NUMS evictor or a later lease blocks the
sweep of its subtree (a member cannot create one by carving, which
keeps the evictor and the lease, spec~0.10.0).
\tr{REWRITE}$_h$ is a graft that publishes its leaves: grounded by
construction, at about $117\vB$ per position of the rewritten subtree
(measured at $h = 6$, \S\ref{sec:batching}) against under 3 per member
for \tr{JOIN}$_8$. A graft also settles off-chain credit as exitable
leaves (\S\ref{sec:receive}).
