% Shared by both versions: the HTLC deadline budget of a channel leaf
% and the hub size it implies.

\paragraph{Deadlines and hub size.} Settlement outputs include one per
in-flight hashed time-locked contract (HTLC). A forwarding node keeps
$\mathsf{cltv\_expiry\_delta}$ blocks between an incoming and an outgoing
HTLC's expiry, and a channel leaf needs
$\mathsf{cltv\_expiry\_delta} \ge G_{\mathrm{exit}} + 1 + \beta_{\mathrm{chan}} + 1 + \mathsf{csv\_delay} + 1 + G_{\mathrm{sweep}}$,
with $\mathsf{csv\_delay}$ the settlement's relative delay,
$G_{\mathrm{sweep}}$ the time to confirm an HTLC sweep,
$G_{\mathrm{exit}}$ the time to confirm the exit, $\lat(q)$ under [C],
and $\beta_{\mathrm{chan}}$ the stale updates the counterparty confirms
ahead of the honest one, one block each, which it buys at about
$313\vB$ a block against the honest party's bid (spec C.4.4). For a
leaf that receives, the binding value is the hub's
$\mathsf{min\_final\_cltv\_expiry\_delta}$ in the invoice; for one that
pays, the hub's delta on the leaf-facing hop. With
$\mathsf{csv\_delay} = 144$, $G_{\mathrm{sweep}} = 2$,
$G_{\mathrm{exit}} = 72$ and $\beta_{\mathrm{chan}} = 0$ this is about
220 blocks, against lnd's default of 80~\cite{lnd}. At $\lat_L = 1$, $G_{\mathrm{exit}} = 72$ needs
$\beta + q \le 71\kappa$; with $\kappa = 25$ and $\beta = 0$, about
1{,}775 channel leaves may close in one window, and larger hubs shard.
The counterparty is normally the operator, which can issue competing
spends, so the budget holds only while the member can outbid them, which
is what $\beta$ and $\beta_{\mathrm{chan}}$ assume; both parties keep a
confirmed fee coin and a reserve that grows with the HTLC value in
flight (spec C.5.5). MID allows seven HTLCs per state beside two balances
(the 520-byte element limit) and $2^{31}$ satoshis per tree.
